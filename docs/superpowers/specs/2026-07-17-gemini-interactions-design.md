# Gemini Interactions API Integration Design

**Date:** 2026-07-17  
**Status:** Approved  
**Scope:** Make Gemini the default LLM provider for Crypto Desk while retaining OpenAI as an explicitly selectable provider.

## Goals

- Use the native Google GenAI SDK and Gemini Interactions API.
- Make Gemini the default provider without removing the existing OpenAI integration.
- Keep one provider fixed for the entire analysis run; never switch providers automatically mid-run.
- Preserve structured Pydantic contracts, the single retry on invalid output, and the final `NO_TRADE` safety behavior.
- Permit only explicitly allowlisted Stable Gemini models in production.
- Record enough model provenance to audit every committee stage without persisting secrets.

## Non-goals

- Automatic fallback between Gemini and OpenAI.
- Runtime load balancing or provider routing.
- Supporting providers other than Gemini and OpenAI.
- Replacing the deterministic risk engine with model output.
- Using Gemini Preview or experimental models in production.

## Selected Approach

Add a native `GeminiStructuredClient` that implements the existing `StructuredClient` protocol. It will call `client.interactions.create()` from the `google-genai` package and request `application/json` output using the JSON Schema generated by the existing Pydantic response model.

The response text will be validated locally with Pydantic before it enters the committee workflow. This keeps the provider boundary narrow and leaves the analyst, bull/bear debate, manager, retry, and `NO_TRADE` orchestration provider-independent.

The OpenAI compatibility endpoint is intentionally not used. Although it would require fewer initial changes, it would couple Gemini behavior to a compatibility layer and make provider-specific diagnostics and future Interactions API features harder to use.

## Configuration

The model configuration gains an explicit provider and provider-neutral reasoning levels:

```yaml
models:
  provider: gemini
  quick: gemini-3.5-flash
  deep: gemini-3.5-flash
  quick_thinking: low
  deep_thinking: high
  debate_rounds: 2
```

`gemini-3.5-flash` is the initial default for both roles because it is a Stable model. The roles remain distinct through their prompts and thinking configuration. Model names remain configurable so a later Stable model can be adopted deliberately.

For `provider: openai`, the existing OpenAI model names remain valid. Provider-specific validation prevents a Gemini model from being paired with the OpenAI adapter or vice versa.

Production configuration rejects Gemini model names that are not in a code-owned Stable allowlist. The allowlist is changed only through a reviewed release; the application does not infer stability from a model name or query a mutable remote catalog during startup.

Secrets remain environment-only:

- Gemini: `GEMINI_API_KEY`
- OpenAI: `OPENAI_API_KEY`

Neither value may appear in logs, reports, SQLite rows, doctor output, or exception messages produced by Crypto Desk.

## Provider Construction and Run Isolation

A small provider factory constructs exactly one structured client when a command starts:

- `gemini` creates the Google GenAI client and wraps it in `GeminiStructuredClient`.
- `openai` creates the existing OpenAI client and wraps it in `OpenAIStructuredClient`.
- Unknown providers fail configuration validation before analysis begins.

The selected client, provider, and resolved quick/deep model configuration are captured in the run context. All committee stages use that same context. A provider error never causes an implicit call to the other provider.

Changing providers is an operator action through YAML or a supported CLI override, followed by a new run.

## Gemini Structured Output Contract

For each committee stage, `GeminiStructuredClient.generate()`:

1. Combines the stage system instructions and serialized evidence payload into a deterministic request input.
2. Calls the Interactions API with the configured model.
3. Supplies a response format containing:
   - `type: text`
   - `mime_type: application/json`
   - the Pydantic model's JSON Schema
4. Reads `interaction.output_text`.
5. Validates the JSON with `response_model.model_validate_json()`.
6. Returns the validated Pydantic object to the existing committee.

Transport errors, empty output, malformed JSON, schema violations, safety blocks, and unsupported response shapes are normalized into provider errors that contain no API key or complete sensitive payload.

The existing committee policy remains authoritative: invalid structured output is retried once. If the retry fails, the analysis resolves to `NO_TRADE`. No model response can bypass deterministic evidence or risk checks.

## Thinking Levels

Configuration uses provider-neutral values `low` and `high`. The Gemini adapter maps these values to the SDK's supported thinking controls. The OpenAI adapter maps them to its supported reasoning controls where applicable, or preserves its current behavior if no mapping is required.

An unsupported thinking value fails validation rather than being silently ignored. The exact wire-level SDK fields will be covered by adapter tests so SDK upgrades cannot change this behavior unnoticed.

## Provenance and Persistence

Every LLM stage records:

- provider
- model
- thinking level
- stage name
- request timestamp
- response timestamp
- success or normalized failure category

API keys and full raw SDK objects are never persisted. Existing evidence, decision, and report artifacts retain their current structure unless a backward-compatible metadata field is needed. Provenance must be present in the machine-readable run artifact so a decision can be reconstructed and audited.

## CLI and Doctor Behavior

User-facing commands keep their existing names. `desk analyze` and scheduled full analysis use the configured provider.

`desk doctor` becomes provider-aware:

- Reports whether the selected provider's API key is present without displaying it.
- Validates provider/model compatibility and the Stable Gemini allowlist offline.
- Performs a minimal structured-output request only in the command's existing online/smoke mode.
- Reports the inactive provider as optional rather than failed.

The doctor command must clearly distinguish configuration failure, authentication failure, rate limiting, network failure, invalid structured output, and an unavailable model.

## Dependency and Documentation Changes

- Add and pin `google-genai` through `uv`.
- Retain the pinned `openai` dependency.
- Regenerate `uv.lock`.
- Add `GEMINI_API_KEY` to `.env.example`.
- Update `config.example.yaml` to select Gemini by default.
- Update the README with Gemini setup, explicit OpenAI switching, and the no-auto-fallback rule.

## Testing Strategy

All normal tests are network-free.

Unit tests cover:

- Gemini request construction and JSON Schema forwarding.
- Successful Pydantic validation.
- Empty, malformed, and schema-invalid outputs.
- Secret-safe normalized errors.
- Stable-model allowlist enforcement.
- Provider/model mismatch and unknown providers.
- Thinking-level mapping.
- Provider factory selection.
- OpenAI compatibility after the configuration change.

Committee tests cover:

- One Gemini client used for every stage in a run.
- No OpenAI call after a Gemini failure.
- One retry for invalid Gemini structured output, followed by `NO_TRADE`.
- Provider/model provenance in artifacts.

CLI tests cover:

- Gemini is the default in example configuration.
- Provider-aware doctor output.
- Missing `GEMINI_API_KEY`.
- Explicit OpenAI selection.

An authenticated online smoke test is opt-in and verifies one small Gemini structured-output request. It is not part of the default test suite or CI because it consumes quota and depends on external state.

## Rollout

1. Add configuration validation and provider factory while retaining OpenAI behavior.
2. Add the Gemini adapter with mocked SDK tests.
3. Make Gemini the example/default provider and update doctor and documentation.
4. Run the full offline suite.
5. Run the opt-in Gemini smoke test with a real `GEMINI_API_KEY`.
6. Execute one dry-run analysis and inspect provenance and `NO_TRADE` behavior before enabling the scheduled daily analysis.

Rollback requires changing `models.provider` to `openai` and restoring OpenAI model names. It does not require code changes and never occurs automatically within a run.

## Acceptance Criteria

- A valid Gemini run completes the full committee with structured Pydantic outputs.
- Gemini is selected by default; OpenAI remains explicitly selectable.
- Every stage in one run uses the same provider.
- Preview or unknown Gemini models are rejected in production configuration.
- Invalid Gemini output retries once and then produces `NO_TRADE`.
- Reports and persisted data contain provider/model provenance but no secret.
- Existing OpenAI tests continue to pass.
- The full offline test, lint, format, lock, and compile checks pass.
- An opt-in authenticated Gemini smoke test succeeds before scheduled production use.
